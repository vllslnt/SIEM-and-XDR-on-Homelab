## Understanding the Alerts and How to Tune Them
Before the alerts are tuned, there are many alerts that appeared from Suricata on the Wazuh dashboard. Due to this, knowing which alerts are crucial and which are noise is very important.

### 1. Check for the most recurring alert from eve.json
In our case, the alert with "SURICATA Ethertype Unknown" signature is often recurring. So, We'll have to check it with:

<b>BASH</b>
```bash
$ sudo grep -c '"signature":"SURICATA Ethertype unknown"' /var/log/suricata/eve.json
```

### 2. Find out when the first time the alert appears

```bash
$ sudo grep '"signature":"SURICATA Ethertype unknown"' /var/log/suricata/eve.json | head -n 1
```

Then, discover the time frame by figuring out the latest occurence of the alert.

```bash
$ sudo grep '"signature":"SURICATA Ethertype unknown"' /var/log/suricata/eve.json | tail -n 1
```

Once the time frame has been discovered, we have to find out how the alerts are distributed.

```bash
$ sudo grep '"signature":"SURICATA Ethertype unknown"' /var/log/suricata/eve.json | tail -n 5
```

### 3. Check for Recent Alerts

```bash
$ sudo tail -n 20 /var/log/suricata/eve.json
```

To confirm that Suricata is working and is producing logs, there should be entries with the "event_type" of "flow".

### 4. Filter for Suricata Events on Wazuh

Log in to the Wazuh dashboard, then head to <kbd>Threat Detection</kbd>, then open the <kbd>Events</kbd> tab, type in "suricata" on the search bar, and filter out the <kbd>Fields</kbd> for:
* timestamp
* agent.name
* rule.description
* rule.level
* rule.id
* rule.groups
* data.alert.signature
* data.alert.category
* data.alert.severity
* data.src_ip
* data.dest_ip
* data.proto

| Field | Value | Meaning |
| -------- | -------- | ---------------- |
| rule.description | Suricata: Alert - SURICATA Ethertype unknown | Wazuh's description |
| Wazuh's description | 3 | Wazuh severity |
| rule.id | 86601 | Wazuh rule that matched the Suricata event |
| rule.groups | ids, suricata | Wazuh has correctly classified it as an IDS/Suricata event |
| data.alert.category | Generic Protocol Command | Suricata's classification |
| data.alert.severity | 3 | Suricata's severity |

### 5. Inspecting the suricata rule
Head over to Wazuh's ossec directory to figure out the pre-determined alert id's.

```bash
$ sudo sed -n '/<rule id="86601"/,/<\/rule>/p' /var/ossec/ruleset/rules/0475-suricata_rules.xml
# 0475-suricata_rules.xml is the file in which rule 86600 is defined as the root or "parent" rule.
```

The output:

```
<rule id="86601" level="3">
    <if_sid>86600</if_sid>
    <field name="event_type">^alert$</field>
    <description>Suricata: Alert - $(alert.signature)</description>
    <options>no_full_log</options>
</rule>
```
Rule 86600 is a default rule on Wazuh that functions as a parent rule that encompasses all incident logs from Suricata's IDS/IPS.

## Filtering for Useful Alerts

### 1. Filter for suricata through rule.groups
In Wazuh threat hunting section, apply the filter for rule.groups and set it to "is", followed by entering the value "suricata". This will narrow down the alerts that are generated by suricata in the dashboard.

In our case, we found an alert with the description "<kbd>Suricata: Alert - ET SCAN Potential SSH Scan OUTBOUND</kbd>". With a severity rating of 2, which warrants an investigation from an analyst.<br>
<i>Severity rating is defined from a scale of 4 to 1, with 1 being the most critical.</i>

### 2. Investigate the alert
<kbd><b>Suricata: Alert - ET SCAN Potential SSH Scan OUTBOUND</b></kbd>
* ET stands for "Emerging Threats", which is about network behaviour.
* OUTBOUND states that the traffic originated from a system that's being monitored by Wazuh and Suricata, heading to another host.

Although this might appear malicious, it's not necessarily a sign of compromise.

<b>To investigate, we need to enable these fields to be viewed on wazuh:<br></b>

<kbd>timestamp</kbd>: The date and time in which the alert was logged<br>
<kbd>agent.name</kbd>: The name of the device in which agent that captured the activity<br>
<kbd>rule.description</kbd>: The description of the alert (in this case, it was given by Suricata)<br>
<kbd>rule.level</kbd>: Refers to the detection rule based on Wazuh's standard (ranging from 0 to 16)<br>
<kbd>rule.id</kbd>: Refers to either Suricata's signature IDs or Wazuh's decoder rule ID for a specific log<br>
<kbd>rule.groups</kbd>: Represents the category or group assigned to a matched Wazuh decoder/rule<br>
<kbd>data.alert.signature</kbd>: The description of the rule that was broken, triggering an intrustion detection alert<br>
<kbd>data.alert.category</kbd>: Represents the Suricata rule classification category (classtype) assigned to a network security event.<br>
<kbd>data.alert.severity</kbd>: Represents the original priority level assigned to a network event by Suricata, where 1 is the highest severity (most critical) and lower numbers or 4 represent minor or informational priority.<br>
<kbd>data.src_ip</kbd>: The source IP address extracted from Suricata's json logs<br>
<kbd>data.dest_ip</kbd>: The destination IP address extracted from Suricata's json logs<br>
<kbd>data.proto</kbd>: Represents the Layer 4 network protocol (such as TCP, UDP, or ICMP) extracted from an integrated Suricata event log<br>
<kbd>data.dest_port</kbd>: The destination port extracted from Suricata's json logs<br>
<kbd>data.src_port</kbd>: The source port extracted from Suricata's json logs

### 3. Using previous techniques to carry out the investigation

<b>BASH</b>
```bash
$ ip neigh show <server IP address>
$ sudo grep '"ET SCAN Potential SSH Scan OUTBOUND"' /var/log/suricata/eve.json | tail -n 1
```
From the output of these commands, look for timestamps, src_ip, dest_ip and proto within the suricata json file to confirm the event log that appears on Wazuh.

```bash
$ sudo grep -c '"ET SCAN Potential SSH Scan OUTBOUND"' /var/log/suricata/eve.json
# Use the -c flag to count the event log with the description "'ET SCAN Potential SSH Scan OUTBOUND'" to find out the frequency
```

We have discovered that the timestamp of the ET log happened on <b>"timestamp":"2026-07-31T11:26:47.938013+0000"</b><br>
With this new information, we can narrow down the log search based on the range of the timestamp.

```bash
$ sudo journalctl --since "2026-07-31 11:25:00" --until "2026-07-31 11:28:00"
# This will output logs that appeared between the set time frame, declared by using --since and --until, from systemd-journald (central logging service)
$ sudo journalctl -k | grep '\[UFW BLOCK\]' | tail -20
# If UFW is enabled, use this to inspect the latest connections blocked by UFW, for good measure
```

During this time, we could see that there is a SFTP connection that was made 7 seconds before the timestamp of the ET log.<br>
This is indicated by the command "<kbd>COMMAND=/usr/bin/sftp</kbd>", and the destination IP represents the direct dotted-quad IP notation of the port that was used for sftp.

### 4. Confirming the absence of unauthorized logins

```bash
$ sudo ufw status verbose
# To check if UFW is enabled
$ sudo sshd -T | grep -E 'permitrootlogin|passwordauthentication|pubkeyauthentication|port'
$ getent passwd | grep -E '/(bash|sh|zsh)$'
# To check SSH configurations, and audits user accounts that have interactive login shells in the system
$ getent group sudo
# Checks which group has sudo privileges
$ sudo grep -R '^[^#].*ALL=' /etc/sudoers /etc/sudoers.d/ 2>/dev/null
# Checks which users has sudo privileges
```

```bash
$ sudo ausearch -m USER_LOGIN --success yes | tail -20
# Checks for successful logins using auditd if installed
```
